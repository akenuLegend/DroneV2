# Parameter handbook — configuration `0xA41F1001`

## 1. How to use this handbook

This handbook describes the authoritative current values in
`drone_alt_hold_1m.ino` (`FC`) and `sender_1m/sender_1m.ino` (`TX`). Line
locations are approximate and the symbol name is authoritative. Values are
software configuration, not proof of installed-airframe suitability.

Every row provides the requested fields. The section and “Subsystem / meaning”
column identify the subsystem. “Increase / high” and “Decrease / low” combine
directional effect with symptoms when excessive. “Safe direction / step” is a
test recommendation, not permission to fly. “Hold” means there is no evidence-
based numeric change; first collect the named observations using
`TEST_PLAN.md`. Change one parameter family at a time, assign a new config
signature, and retain an old/new/unit/reason/risk/rollback ledger.

Telemetry names below refer either to the sender `STATUS` subset or to fields
carried by telemetry v5. The current sender prints `cfg`, mode/phase/reason,
`z/sp/vz/src/corr`, altitude velocity setpoint/integral, pitch/roll, motor and
hover values, flow/position values, ages/quality/strength, loop/dt/overruns and
MTF/BMP/task diagnostics. The packet also carries yaw/rates, controller outputs,
attitude I terms, biases, vibration/clip and radio counters, but `STATUS` does
not print them. Any row that needs those fields requires a traceable packet
decoder or diagnostic build as a prerequisite. The 248-byte packet itself does
not expose raw sensor innovations, per-axis saturation causes, battery, RPM, or
stack margin; those observations are explicitly marked unavailable.

## 17. Parameters that remain UNKNOWN or unavailable

- Actual CPU frequency, Arduino `loopTask` affinity/priority, task stack
  high-water, WCET/jitter, installed MTF publish latency/rate, BMP conversion
  latency/rate, filter group delay, flow error versus quality/surface/height,
  per-motor thrust/current/RPM, battery sag, frame CG, and current-build flight
  stability are UNKNOWN.
- There is no evidence-based control-deadline trip threshold. `dt` telemetry is
  for measurement; do not turn it into a safety transition until runtime and
  airframe response data justify a policy.
- No handbook recommendation overrides the missing battery failsafe,
  independent hardware kill, ESC feedback, redundant IMU, or persistent log
  gaps in `FINAL_SYSTEM_AUDIT.md`.
- The next action for any “Hold” row is data collection, not a guessed numeric
  edit. Follow `TEST_PLAN.md`, stop at the first failed gate, and keep free
  flight prohibited until all earlier gates have objective evidence.
